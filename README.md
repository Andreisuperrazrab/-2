# Bounty Hunter — лабораторна робота № 5

**Дисципліна:** Web-дизайн та Web-програмування · **Тема:** Розроблення вебзастосунку з використанням технологій вайбкодингу.

Це розширення наявного проєкту Bounty Hunter (клієнська частина з попередніх робіт). Дизайн, HTML-сторінки та CSS-змінні збережено. Замість масивів фіктивних даних і `sessionStorage` для заявок/чату використовуються **REST API та SQLite**.

## Швидкий запуск на Windows / macOS / Linux

1. Розпакуйте архів; відкрийте папку, у якій лежить `package.json`.
2. Установіть **Node.js 22.13+** (рекомендовано поточну підтримувану LTS із модулем `node:sqlite`). Перевірте `node -v`.
3. **У PowerShell** виконайте:

   ```powershell
   $env:DEMO_SEED = "1"
   $env:PORT = "3000"
   npm start
   ```

   **У Linux/macOS:** `DEMO_SEED=1 PORT=3000 npm start`.
4. Перейдіть у браузері на **http://localhost:3000/**. Перевірте здоров’я БД: **http://localhost:3000/api/health**.
5. Для тестування запустіть у другому терміналі `npm test` (потрібен лише Node.js). `npm install` **не потрібен** — зовнішніх npm-залежностей немає.

> Якщо браузер не з’єднується з `localhost`, перевірте запущений сервер та порт. Не відкривайте HTML через `file://`: потрібні API й SQLite.

### Демодані (лише локально)

Якщо `DEMO_SEED=1` і база ще порожня, автоматично створяться 3 фрилансери, 3 роботодавці та 3 вакансії (ті самі приклади, що були в початковому архіві). Для перевірки входу використовуйте:

| Роль | Логін | Демопароль |
|---|---|---|
| Фрилансер | `vitalii`, `iryna` або `andrii` | `DemoPass123!` |
| Замовник | `technova`, `dataforge` або `cloudbridge` | `DemoPass123!` |

**Не вмикайте `DEMO_SEED=1` на публічному сайті:** усі демонстраційні облікові записи мають відомий пароль. У production встановіть `DEMO_SEED=0` та зареєструйте власних користувачів.

Зареєструвати нового фрилансера або замовника можна через `register.html`. **Дані не зникають після перезавантаження сторінки**: SQLite-файл створюється в `data/bounty-hunter.sqlite` (або в `DB_PATH`). Для скидання локального стенду зупиніть сервер, видаліть цей файл і запустіть з `DEMO_SEED=1`.

## Основні можливості

- Реєстрація, вхід і вихід; паролі зберігаються як salted `scrypt`-хеші, сесія — в HttpOnly cookie.
- Каталог фрилансерів із пошуком та фільтрами. Деталі профілю та зміна **власного** профілю.
- Каталог вакансій із пошуком та фільтрами, повний CRUD вакансій **лише для замовників-власників**.
- Відгук на вакансію **лише від фрилансера**, захист від повторних заявок.
- Список заявок і їхні статуси; власник вакансії може прийняти або відхилити заявку.
- Переписка між зареєстрованими користувачами з серверним збереженням та обмеженням читання діалогу його учасниками; ручне оновлення повідомлень.
- Демонстраційне звернення до підтримки, яке потрапляє до бази (оператора служби підтримки немає).

## Архітектура

```
Браузер (13 HTML-сторінок + CSS + vanilla JS)
         │ fetch / async / await, JSON
         ▼
Node.js HTTP-server (server/app.js)
  ├─ маршрути REST API, перевірка даних
  ├─ автентифікація, ролі, права доступу
  ├─ статичні ресурси з public/
  └─ SQLite (server/db.js, DB_PATH)
       ├─ users, sessions, profiles
       ├─ jobs, applications, messages
       └─ support_tickets
```

**Технологічне рішення:** замість Express використано штатний `node:http` із маршрутизатором, а замість зовнішнього пакета SQLite — `node:sqlite`. Для вимог ЛР №5 потрібні Node.js, REST API й база даних; Express у методичних матеріалах наведено як інструмент, що спрощує написання маршрутів. Такий вибір дозволяє **гарантовано запустити й протестувати проєкт без `npm install` та доступу до реєстру пакетів**. Якщо викладач **окремо вимагає саме Express**, поточний HTTP-адаптер слід перенести на Express без зміни API та структури БД.

## Перевірка

`npm test` перевіряє реальні HTTP-запити до ізольованого тестового сервера й тимчасової SQLite БД: авторизацію, CRUD, заявки, чат, статуси, обмеження ролей, валідацію, обмеження розміру JSON, Origin та HTTP-заголовки. Фактичні результати: `docs/api-test-results.txt`. Статична перевірка доступності: `python tests/static_audit.py` (потребує BeautifulSoup). Заміри локальних HTTP-запитів: `node tests/benchmark.js`; результат поточного середовища: `docs/performance.json`.

У цьому середовищі Chromium адміністративно блокував відкриття локальних URL. Тому скриншоти зроблено в Chromium із **симуляцією навігації та проксійованими запитами до локального API**, а не з публічно розгорнутого сайту. Методика й результат: `tests/dom_walkthrough.py`, `docs/dom-results.json`. Перед здачею потрібно виконати повний ручний прогін у звичайному браузері.

## Структура

- `public/` — збережена HTML/CSS-основа, `js/main.js` (fetch, DOM, форми).
- `server/db.js` — SQLite-схема й початкові демодані.
- `server/app.js` — Node.js HTTP сервер та REST API.
- `server/index.js` — запуск сервера, `PORT`, `HOST`, `DB_PATH`.
- `tests/` — API-тести, статичні та DOM-перевірки.
- `docs/` — специфікація, API, журнал ШІ, інструкція деплою, результати та скриншоти.
- `Dockerfile`, `compose.yaml` — контейнеризація та іменований том для SQLite.

## Розгортання та обмеження

Репозиторій GitHub і URL публічного сайту **ще не створено від імені одногруппника**. Докладні кроки: [`docs/DEPLOY.md`](docs/DEPLOY.md). **Публічний застосунок потребує HTTPS і постійного диска**, інакше SQLite може втратити записи після рестарту хостингу. Застосунок не має платежів/escrow, відгуків, модерації, відновлення паролів або реального оператора підтримки; він є навчальним MVP, а не готовим комерційним маркетплейсом.

### Перед захистом

1. Перевірити відповідність індивідуальним вимогам із ПР №1 та прототипу Figma одногруппника (вони не були надані разом з архівом).
2. Створити **власний** GitHub-репозиторій одногруппника й завантажити туди проєкт.
3. Розгорнути за інструкцією, перевірити `/api/health`, додати фактичні URL у DOCX-звіт.
4. Відкрити сайт із браузера на ПК і смартфоні, перевірити реальний логін, CRUD, переписку та доступність клавіатурою.
